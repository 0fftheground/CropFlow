# 非代码接入包模板

> 本模板用于当前阶段给各业务方向统一提交“未来接入包”。  
> 适用方向：农事日历 / 生育期、植保、灌溉、施肥、遥感监测、前端。  
> 当前阶段目标是补齐契约、字段和流程说明，不是直接提交正式代码。

---

## 1. 使用场景

适用于以下情况：

```text
1. 核心对象、ER 图、API contract 还在收敛。
2. 当前主线只推进一个方向，但其他方向也要同步准备后续接入材料。
3. 需要把“以后怎么接入”先压成统一格式，避免各方向各写各的。
```

不适用于以下情况：

```text
1. 已经进入正式编码和联调阶段。
2. 已经有稳定的对象结构、OpenAPI 和实现边界。
3. 当前要交的是 adapter / mapper / router / 测试代码。
```

## 2. 统一交付清单

每个方向当前至少提交以下内容：

| 交付项 | 说明 | 最小产出形式 |
|---|---|---|
| 接口摘要 | 外部算法、外部数据源、外部设备或页面依赖摘要 | Markdown 摘要 |
| 字段草案 | 当前方向后续会用到的关键字段 | 字段表 |
| 任务 / 流程 / 分支规则 | 何时触发、如何分支、何时 no_action、何时复核 | 规则表 / 分支说明 |
| 场景表 | 正常、异常、无需动作、需复核等场景 | 场景表 |
| 待决问题清单 | 当前仍需要拍板的问题 | 问题列表 |

方向可按需要额外补充：

```text
1. 任务类型与阶段关系草案。
2. 库存关系说明。
3. 监测结果到下游对象的映射草案。
4. 页面字段需求和演示流程。
5. 设备回调字段或执行模式说明。
```

## 3. 统一提交结构

建议每个方向按下面结构提交一份材料：

```md
# <方向名>非代码接入包

## 1. 当前范围

## 2. 接口摘要

## 3. 字段草案

## 4. 任务 / 流程 / 分支规则

## 5. 场景表

## 6. 待决问题清单
```

## 4. 各章节最少要写什么

### 4.1 当前范围

至少写清：

```text
1. 当前方向这次准备覆盖哪些任务、场景或页面。
2. 明确这次只补材料，不补正式代码。
3. 指出和当前主线方向的关系：直接支撑、后续复用，还是独立准备。
```

推荐模板：

```md
## 1. 当前范围

- 本次覆盖：
- 本次不覆盖：
- 与当前主线的关系：
```

### 4.2 接口摘要

至少写清：

```text
1. 接口或数据源名称。
2. 触发时机或使用时机。
3. 主要输入来源。
4. 主要输出语义。
5. 失败或信息不足时怎么处理。
6. 哪些点还未确认。
```

推荐模板：

```md
## 2. 接口摘要

| 接口 / 数据源 | 用途 | 触发时机 | 主要输入 | 主要输出 | 失败处理 | 待确认 |
|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |
```

### 4.3 字段草案

至少写清：

```text
1. 字段名。
2. 当前语义。
3. 来源。
4. 是否必需。
5. 当前更像输入、输出、执行记录还是评价反馈字段。
6. 是否需要核心后端或产品 / 架构负责人拍板。
```

推荐模板：

```md
## 3. 字段草案

| 字段名 | 当前语义 | 来源 | 是否必需 | 字段类别 | 待拍板 |
|---|---|---|---|---|---|
|  |  |  |  |  |  |
```

字段类别建议统一用：

```text
1. input
2. output
3. operation_plan_candidate
4. execution_feedback_candidate
5. evaluation_feedback_candidate
6. review_context_candidate
```

### 4.4 任务 / 流程 / 分支规则

至少写清：

```text
1. 当前方向有哪些任务或页面语义。
2. 何时进入主流程。
3. 何时 no_action。
4. 何时生成方案或进入执行。
5. 何时需要人工复核。
6. 缺少输入时怎么兜底。
```

推荐模板：

```md
## 4. 任务 / 流程 / 分支规则

| 目标语义 | 触发时机 | 前置条件 | 正常动作 | no_action 条件 | 复核条件 | 兜底动作 |
|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |
```

### 4.5 场景表

至少包含：

```text
1. 正常场景。
2. 无需动作场景。
3. 需人工复核场景。
```

如方向有明显异常分支，建议再加：

```text
4. 输入不足或接口失败场景。
```

推荐模板：

```md
## 5. 场景表

| 场景名 | 输入条件 | 预期结果 | 不应发生 |
|---|---|---|---|
| 正常场景 |  |  |  |
| 无需动作场景 |  |  |  |
| 需复核场景 |  |  |  |
```

### 4.6 待决问题清单

至少写清：

```text
1. 问题本身是什么。
2. 卡在哪个对象、接口或流程上。
3. 需要谁拍板。
4. 如果暂时不拍板，会影响什么。
```

推荐模板：

```md
## 6. 待决问题清单

| 问题 | 影响范围 | 需要谁拍板 | 不拍板的影响 |
|---|---|---|---|
|  |  |  |  |
```

## 5. 各方向补充要求

不同方向在统一结构之外，建议重点补这些内容：

| 方向 | 额外重点 |
|---|---|
| 农事日历 / 生育期 | `stageCode`、CalendarItem 生成条件、阶段变化影响范围 |
| 植保 | 调查字段、方案字段、药后调查字段、补防复核规则 |
| 施肥 | 任务阶段关系、处方图字段、库存关系 |
| 灌溉 | 执行模式、设备回调字段、异常处理和评价反馈 |
| 遥感监测 | 监测结果字段、异常点位语义、下游映射 |
| 前端 | 页面清单、字段缺口、演示流程、回退路径 |

## 6. 完成标准

当前阶段一份合格的非代码接入包，至少满足：

```text
1. 不要求正式代码。
2. 不要求最终核心对象 JSON。
3. 能被核心后端直接拿去收敛模型字段、API contract 和后续实现边界。
4. 所有未定事项都被显式列出，没有“靠口头补充”的关键前提。
5. 能说明该方向未来接入时最小要补的内容，而不是只有零散笔记。
```

## 7. 与现有文档的关系

```text
1. 本模板是统一提交结构。
2. 各方向具体交什么，以 docs/planning/team-work-division/ 下对应方向文档为准。
3. 当前主线排期里如果提到“提交非代码接入包”，默认就是按本模板组织。
```
