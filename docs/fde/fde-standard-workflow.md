# FDE 标准工作流程

> 本文档定义 CropFlow 项目内 Forward Deployed Engineer 的标准工作方式。  
> FDE 的核心职责是把真实业务现场的问题、约束和反馈转化为可开发、可复用、可上线的系统能力，而不是简单转发需求或临时堆定制。

---

## 1. 工作原则

### 1.1 以业务结果为起点

FDE 不从“客户要什么功能”开始，而从“业务要达成什么结果”开始。

```text
1. 先确认业务目标、成功标准和约束。
2. 再判断系统需要新增、配置、集成还是拒绝某些能力。
3. 不把现场口头需求直接等同于产品需求。
```

### 1.2 贴近现场，但不失去产品化判断

FDE 要深入现场理解真实流程，但不能把每个现场例外都做成一次性定制。

```text
1. 能复用的平台能力优先复用。
2. 能配置解决的不写代码。
3. 必须定制时，记录原因、边界、退出条件和后续产品化可能性。
4. 判断一个方案是否值得做，要看是否能沉淀为通用能力或关键客户价值。
```

### 1.3 端到端负责，但不越权拍板

FDE 需要推动问题闭环，但不能替产品、架构、业务 owner 做不可逆决策。

```text
1. FDE 负责澄清事实、提出选项、说明影响。
2. 产品 / 架构负责人负责范围、对象边界和长期取舍。
3. 核心后端负责模型、接口、workflow、job 和工程质量。
4. 业务方向同事负责农艺规则、算法语义和业务事实确认。
```

## 2. 标准流程总览

```text
0. Intake：接收方向或场景，确认是否值得进入 FDE 流程。
1. Discover：访谈现场，获取业务链路、角色、数据、约束和成功标准。
2. Frame：把现场问题翻译成系统问题，定义目标、非目标和优先级。
3. Map：映射到 CropFlow 核心对象、workflow、job、接口和前端场景。
4. Decide：拉齐 owner，确认冻结口径、待决问题和下一阶段进入条件。
5. Build / Enable：推动后端、前端、算法、数据或配置落地。
6. Validate：用真实场景、mock 或测试数据验证结果。
7. Deploy / Adopt：支持联调、上线、培训和使用反馈。
8. Productize：把现场经验回灌为可复用能力、文档、模板或 backlog。
9. Retro：复盘交付质量、可复用性和下一次改进点。
```

## 3. 阶段说明

### 3.1 Intake：接入判断

目标：判断这个方向或场景是否应该现在进入接入流程。

| 输入 | FDE 动作 | 产出 |
|---|---|---|
| 方向需求、口头说明、已有材料 | 快速确认范围、owner、紧急程度、业务价值、依赖和未知点 | intake note |

必须回答：

```text
1. 这个方向现在为什么要接入？
2. 谁是业务 owner、算法 owner、系统 owner？
3. 当前是探索、拆解、实现、联调还是上线阶段？
4. 如果不做，会影响什么？
5. 是否已经有足够信息进入 P0 访谈？
```

退出标准：

```text
1. 已明确 owner。
2. 已明确当前阶段目标。
3. 已明确需要访谈的人和资料。
```

### 3.2 Discover：现场访谈

目标：获取真实业务链路，不急着设计接口。

| 输入 | FDE 动作 | 产出 |
|---|---|---|
| 业务同事、算法同事、前端或实施同事的原始说明 | 访谈、追问、记录事实和缺口 | discovery notes |

重点问题：

```text
1. 当前业务链路从什么事件开始，到什么结果结束？
2. 谁参与，每个角色做什么判断？
3. 哪些判断可以自动化，哪些必须人工判断？
4. 哪些数据是系统已有，哪些来自外部接口，哪些依赖人工录入？
5. 正常、无需动作、异常、信息不足、需复核分别怎么走？
```

退出标准：

```text
1. 主链路能讲通。
2. 关键角色和数据来源清楚。
3. 至少有 3 类场景：正常、无需动作、异常或需复核。
4. 未确认信息已进入待决问题清单。
```

### 3.3 Frame：问题定义

目标：把业务叙述转成系统可以评审的问题定义。

| 输入 | FDE 动作 | 产出 |
|---|---|---|
| discovery notes | 提炼目标、非目标、成功标准、约束、风险 | problem brief |

必须写清：

```text
1. 业务目标。
2. 当前阶段范围。
3. 明确不做什么。
4. 成功标准。
5. 关键约束。
6. 需要谁拍板的待决问题。
```

退出标准：

```text
1. 产品 / 架构负责人能据此判断是否进入拆解。
2. 后端能看出大概会影响哪些对象和流程。
3. 业务同事确认没有误解核心事实。
```

### 3.4 Map：系统映射

目标：把业务问题映射到 CropFlow 统一系统语言。

| 输入 | FDE 动作 | 产出 |
|---|---|---|
| problem brief、接口资料、现有系统文档 | 映射对象、workflow、job、接口、场景和页面 | integration mapping |

映射维度：

```text
1. PlantingPlan：是否依赖计划基础信息。
2. CalendarItem：是否先生成预备农事项。
3. TaskIntent：是否需要表达 no_action、need_more_info、待确认。
4. FarmingTask：什么情况下生成正式任务。
5. OperationPlan：是否需要作业方案或处方方案。
6. Execution / ExecutionRecord：谁执行，如何记录。
7. Evaluation / Feedback：如何评价，反馈是否影响后续编排。
8. ReviewRequest：什么情况下人工复核。
9. InventoryItem / InventoryTransaction：是否涉及库存。
10. EventRecord / Background Job：是否需要事件、定时或轮询。
```

退出标准：

```text
1. 主要对象边界清楚。
2. workflowKey / taskSubtype 有草案。
3. 接口输入输出和系统动作之间的关系能讲通。
4. 不确定点没有被伪装成已冻结结论。
```

### 3.5 Decide：确认和冻结

目标：把可以确认的内容冻结，把不能确认的内容变成明确的下一步。

| 输入 | FDE 动作 | 产出 |
|---|---|---|
| integration mapping、待决问题 | 组织评审，推动 owner 确认 | decision log |

评审顺序：

```text
1. 业务 owner 确认事实和农艺规则。
2. 产品 / 架构负责人确认范围、对象边界和取舍。
3. 核心后端确认 workflow、job、模型和接口拆解。
4. 前端确认页面信息需求和交互草案。
5. 测试或开发负责人确认场景覆盖。
```

退出标准：

```text
1. 冻结口径写入方向文档。
2. 待决问题有 owner 和下一步。
3. 已明确是否进入 P1 后端拆解或继续访谈。
```

### 3.6 Build / Enable：推动落地

目标：让实现团队基于一致材料推进，不让口头信息散落。

| 输入 | FDE 动作 | 产出 |
|---|---|---|
| 冻结口径、接口资料、场景表 | 协助拆任务、解释上下文、补文档、处理歧义 | implementation support |

FDE 在此阶段主要做：

```text
1. 帮后端解释业务字段和分支。
2. 帮算法同事确认字段来源和异常语义。
3. 帮前端确认用户视角和展示优先级。
4. 发现需求变化时，先回到 decision log，不直接改实现口径。
5. 把实现中新增的事实回写文档。
```

退出标准：

```text
1. 后端拆解不再依赖口头解释。
2. 关键接口和对象映射可追溯到文档。
3. 新增变更都有明确 owner 和原因。
```

### 3.7 Validate：场景验证

目标：证明系统行为满足业务场景，不只证明接口能调用。

| 输入 | FDE 动作 | 产出 |
|---|---|---|
| 实现结果、测试环境、mock 或真实样例 | 跑通场景，记录偏差和修正建议 | validation report |

至少验证：

```text
1. 正常主链路。
2. 无需动作链路。
3. 信息不足或接口失败链路。
4. 需人工复核链路。
5. 关键字段在后端、前端、执行反馈中的一致性。
```

退出标准：

```text
1. 场景表中的主场景有验证结论。
2. 偏差被记录为 bug、待决问题或范围外。
3. 业务 owner 确认行为符合预期。
```

### 3.8 Deploy / Adopt：联调和使用

目标：帮助能力进入真实使用，而不是停在开发完成。

| 输入 | FDE 动作 | 产出 |
|---|---|---|
| 可运行能力、联调环境、用户反馈 | 支持联调、演示、培训、问题分流 | adoption notes |

关注点：

```text
1. 用户是否理解状态和操作。
2. 真实数据是否暴露新的边界条件。
3. 接口失败或人工流程是否有兜底。
4. 是否出现大量现场 workaround。
5. 是否有必要调整产品默认行为。
```

退出标准：

```text
1. 关键用户能按预期完成主流程。
2. 已知问题分级进入 bug、backlog 或待决问题。
3. 文档和 mock 与实际行为一致。
```

### 3.9 Productize：产品化沉淀

目标：把一次现场接入转化为后续可复用资产。

| 输入 | FDE 动作 | 产出 |
|---|---|---|
| 验证结果、用户反馈、实现差异 | 提炼可复用模式、更新模板和 backlog | productization notes |

需要判断：

```text
1. 哪些能力是方向专属。
2. 哪些能力应沉淀为通用 workflow、job、字段或页面模式。
3. 哪些 workaround 应该清理。
4. 哪些决策需要补到 docs/decisions。
5. 哪些经验应更新到模板或指南。
```

退出标准：

```text
1. 可复用部分已进入文档或 backlog。
2. 一次性定制有保留理由和退出条件。
3. 后续方向能复用本次经验。
```

### 3.10 Retro：复盘

目标：改进 FDE 流程本身。

| 输入 | FDE 动作 | 产出 |
|---|---|---|
| 交付过程、缺口、返工、延期、反馈 | 复盘流程和材料质量 | retro note |

复盘问题：

```text
1. 哪些信息一开始没问到，导致后续返工？
2. 哪些字段或分支本应更早冻结？
3. 哪些文档对开发最有帮助？
4. 哪些口头沟通应该沉淀为模板？
5. 下一个方向接入时应提前问什么？
```

## 4. 标准节奏

### 4.1 单方向接入建议节奏

```text
Day 0：Intake，确认 owner 和资料。
Day 1-2：Discover，完成关键访谈。
Day 3：Frame + Map，形成 P0 草案。
Day 4：业务 owner 和产品 / 架构评审。
Day 5：补齐 P1 拆解材料或继续访谈。
后续：随实现进入 Build / Validate / Deploy / Productize。
```

实际节奏可调整，但原则是：

```text
1. 先收敛 P0，再进入 P1。
2. 不把 P2 前端 contract 提前伪装成 P0 材料。
3. 每次评审只冻结当前能确认的事实。
```

### 4.2 每周 FDE 例会建议

```text
1. 本周完成了哪些方向的 P0 / P1 / P2。
2. 哪些问题需要产品 / 架构负责人拍板。
3. 哪些接口或字段阻断后端拆解。
4. 哪些现场反馈需要产品化。
5. 下周最重要的 1-3 个推进目标。
```

## 5. 标准产物清单

| 产物 | 何时产生 | 作用 |
|---|---|---|
| intake note | 接入开始 | 判断是否值得进入 FDE 流程 |
| discovery notes | 访谈阶段 | 保留业务事实和原始上下文 |
| problem brief | 问题定义阶段 | 统一目标、范围、非目标、成功标准 |
| integration mapping | 系统映射阶段 | 连接业务链路和 CropFlow 对象 |
| decision log | 评审阶段 | 记录冻结口径和待决问题 |
| validation report | 验证阶段 | 证明场景是否跑通 |
| adoption notes | 联调 / 使用阶段 | 记录真实使用问题和反馈 |
| productization notes | 产品化阶段 | 沉淀可复用能力和 backlog |
| retro note | 收尾阶段 | 改进下一次接入流程 |

## 6. 质量标准

一份合格的 FDE 产物应满足：

```text
1. 能区分事实、推断、假设和待确认问题。
2. 能说明业务目标，不只是列功能点。
3. 能映射到系统对象，不只是贴业务流程图。
4. 能覆盖异常和 no_action，不只写正常路径。
5. 能说明 owner 和下一步，不留下无主问题。
6. 能被后端、前端、算法、产品分别消费。
7. 能让下一个方向复用，而不是只服务一次会议。
```

## 7. 常见反模式

```text
1. 需求搬运：把业务同事的话原样放入文档，不做系统翻译。
2. 过早接口化：业务链路没清楚，就开始写 FastAPI contract。
3. 伪确定性：为了推进，把未知字段、状态或规则写成已确认。
4. 现场定制失控：每个方向都做一次性逻辑，不判断复用价值。
5. 只有正常路径：不追问 no_action、失败、信息不足和人工复核。
6. 只关注上线：没有把现场反馈回灌为产品能力或模板。
7. owner 缺失：问题写了很多，但没有谁确认、何时确认。
```

## 9. 行业参考

本文档参考了公开行业资料中的共识，并结合 CropFlow 当前项目约束做了裁剪：

```text
1. Palantir 对 FDSE 的定位：围绕客户的技术和运营结果，强调 one customer, many capabilities。
2. Built In 对 FDE 的总结：嵌入式协作、面向结果构建、作为客户和产品 / 工程之间的反馈回路。
3. Gainsight / Intercom 案例：FDE 不应只是专业服务，而应把客户摩擦点转化为可规模化产品改进。
4. Rocketlane 对复杂企业实施的总结：FDE 需要快速理解真实环境、处理边界条件、打通 GTM / Product / Engineering。
5. MBAssett 对 FDE 评估的总结：重点不是只会沟通或只会写代码，而是问题判断、产品判断、工程执行和不确定性沟通。
```
